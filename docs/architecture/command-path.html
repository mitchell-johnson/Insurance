How a command is applied, and how a day is closed

Read from the code on main, 14 Nov 2026 (crates/api, crates/raft, crates/core, crates/workflows). The same path serves every caller: a person through the portal, the insurer's own systems, a module's outbox, the close.

One command, from caller to ledger

1Caller

Sends a typed command with an idempotency key it derives from its own state, so a retry after a timeout applies once.

→

2ic-api

Checks the Entra token and that the role may send this command (allowed_callers()). Value leaving a policy is put to the people master first.

→

3Route

Finds the partition: by group (a fixed hash of its ID, 64 partitions), by policy, or by asking every partition for a policy number.

→

4Partition leader

Appends to its Raft log. A majority of the three nodes must fsync the entry before it commits. A leader change mid-way is retried with the same key.

→

5State machine

Applies the entry on every replica: policy state, double-entry postings on the hash chain, claims, read models. No clock, no randomness, bounded work. Same log, same state hash.

→

6Reply

The result, or the original result for a repeated key. 503 with Retry-After if there is no majority; nothing acknowledged is ever lost.

What the partition leader then does, at least once and resumed by the next leader

7Events

A gapless stream EventRecord {partition, seq}, no personal data, published to Event Hubs policy-events.

→

8Modules read them

Each module group on the nodes turns events into its own commands, keeps a checkpoint per partition and asks for gaps.

→

9Module outbox

Commands a module owes the core (commission, payments settled, prices, discounts) leave through its outbox and re-enter at step 4 as a named caller.

→

10Drivers

Stateless processes act on a module's outbox outside: the bank, letters, files to reinsurers, extracts. Each result comes back as a command.

→

11Cross-partition

Policy transfers and claims offsets go as messages retried until acknowledged, with money held in transit and checked daily.

→

12Sealing

Finished stretches of the journal sealed to write-once Blob Storage (cold-segments).

The daily close (CronJob ic-close at 00:05 New Zealand time, a Temporal workflow on ic-worker)

ACutoff

Each partition stops taking the day, for every business day whose midnight has passed, oldest first. The date moves only here; nothing reads the wall clock.

→

BRounds, in chunks

Policy work per partition in bounded chunks: billing, arrears and lapses (held until a proven lapse notice allows), earning, anniversaries. Then unit orders at struck prices.

→

CReconciliation

Each partition's books are checked. A break fails the close, the day stays open and the next is not started.

→

DSigned Merkle root

Every partition's ledger head folded into a root, signed with the Key Vault key, written to write-once merkle-roots.

→

ENext day open

Each step is safe to repeat by any worker; a worker that dies is replaced from Temporal's record of the last finished step.

Proving a day later: recompute the root from the ledger heads at that date and check the signature against the key version named in the blob (docs/operations.md, "Proving a closed day"). Finance's month-end close is a separate module process (ic-finance-close) that reads these signed roots.
